# 文档知识维护

类型：`documentation-index`

本页维护文档的归属、效力和修正规则。项目开发规则以
[CLAUDE.md](../CLAUDE.md)为准，文档导航见 [总入口](00-index.md)。

## 一个问题由一处正文负责

规划、ADR、方案、验证矩阵和完成记录在开头写明能力归属。
Core／Editor 的职责及跨层方案要求以
[项目规则](../CLAUDE.md#规划与方案必须明确能力归属)为准；
归属与依赖分开表达，完成状态按所属能力分别记录。
Editor 的 Core 缺口建议须关联 GEF → Draw2D → Novadraw Core 的依赖证据，
并记录停止新增与恢复条件；规则见
[Core 依赖门禁](../CLAUDE.md#editor-缺失-core-依赖时停止新增)。

概览负责边界和阅读路线；专题负责完整行为；ADR 负责为什么选择；parity 负责采用
外部语义；roadmap 负责执行状态；review 负责某次快照的发现和结果。
其他文件用链接引用，不复制完整算法、签名表、状态表或实施日志。

目录按知识来源和规范效力划分，主题作为第二层。小文件若有独立 owner、输入/输出、
错误和扩展边界，应保留；只有表述差异或重复展开才合并。大文件先删除重复，再按
独立问题拆分，避免仅凭行数制造新碎片。

## 冲突与替代关系

1. 已接受 ADR 的明确替代关系决定关键取舍；历史批准可以被有证据的修订取代。
2. 独立接受的 design 在明确记录的范围内具有规范效力。替代旧 design 时，记录
   接受依据、日期、修订及被替代章节，并同步旧入口；不要求另建 ADR。
   未被替代的条款继续有效，影响长期架构边界的选择仍按 ADR 规则评审。
3. `normative-design` 中范围更窄的专题优先于总览；局部接受的 `proposal` 只通过
   明确链接的已接受专题提供合同，其余候选不具有覆盖效力。
4. reference 服从源码事实；parity 解释映射，二者不覆盖 Novadraw 设计。
5. roadmap、review、迁移方法和 archive 不定义运行时契约。

设计与实现不一致时，先判断是实现缺陷、新约束需要设计修订，还是尚未完成。
不得把文档直接改成代码现状。只有核对公开路径或证明已有契约时才定向查实现，
理想架构设计仍遵守禁止先扫项目 Rust 的规则。

## 当前表达与原始证据

可服务的知识表达可以删除、归并或重写。原始日志、JSON、探针、基线快照和校验
manifest 保持只增不改；review 的原判断和完成事实保留在其原基线中。
旧稿全文不应继续处于当前设计阅读路径。

逐轮评审、逐项回应和实施流水归并成稳定的专题结论，保留已接受范围、最新验证
分母、未完成项与恢复条件。当前入口不重复罗列每轮中间状态。
性能比较保留判断所需的匹配前后数据、配置和限制；不同负载、版本或统计口径的
数字作为独立历史基线，不合并计算提速比。正文保留独立契约及待证明边界，
过程稿通过归档入口追溯。

删除已取代方案时，保存原始字节、路径和 SHA-256，并记录新入口。
历史报告引用旧方案时可指向对应快照；其正文判断不改成新结论。
迁出编号从归并记录映射到当前正文与原始快照，不为具体方案保留空壳。
默认架构检索排除 archive，历史追溯时显式进入。

文本性能验证的日志、原始样本、收据、构建记录及生成快照属于本地中间产物，
统一放在 `target/verification/text-*/`，不纳入 Git。`doc` 只保留验证报告和
简短的本地产物指引；报告记录方法、结果、限制及必要的哈希。迁移中间产物时
核对 SHA-256，保留原始字节；冻结收据中的历史路径不作改写。

其他已提交的历史原始证据放在 `doc/verification/evidence/`；独立字体比较报告及其原始
GPU demos 放在 `doc/reference/fonts/reports/`。这两类快照允许整体迁移，内容仍保持
只增不改；其内部历史路径保留，不按当前文档改写。文档门禁检查当前报告入口，
不把冻结证据和原始 demos 当作现行规范文档。迁移后核对文件 SHA-256。

源码和工具的目录归属见 [根目录说明](../README.md)；可执行测试入口见
[tests/README.md](../tests/README.md)。本地生成物统一放在 `target/`。

## 文档类型

### ADR 与具体设计分开维护

普通方案默认放在 `doc/design/`，按主题命名，不分配 ADR 编号。
设计可以独立评审、接受；设计与 ADR 无需一一对应，也可直接引用已有 ADR。
接受时记录范围与依据，不因评审通过而补建 ADR。

`architecture-decision` 只用于影响长期架构边界的选择。正文须说明问题、采用的
选择、替代方案为何不采用、取舍与后果，以及关联设计。不能仅因修改公开 API、
新增能力、性能优化、通过评审或篇幅较大，就把方案放进 ADR。

`normative-design` 负责已接受的运行协议：owner、输入输出、身份与版本、算法、
状态、失败、扩展点和成本。候选使用 `proposal`。混合文档拆开后，ADR 链接设计，
设计引用相关决策；接受日期与修订效力保持，执行状态仍由 roadmap 负责。
具体策略、组件组合、参数公式和平台适配通常放在 design；外部源码事实放在
reference，采用差异放在 parity，测试矩阵与某次结果分别放在 verification 的
plans 与 reviews。

已迁出 ADR 的方案不保留一篇冒充决策的空壳。更新当前引用，在归档入口保留
原编号与新入口的对应；真正被替代的决策可保留简短替代记录，编号不重排或复用。

标题后写 `类型：` 标记。入口页使用 `documentation-index`；正文按内容选用：

| 用途 | 类型 |
|---|---|
| 当前契约、关键决策、候选 | `normative-design`、`architecture-decision`、`proposal` |
| 源码事实、采用关系 | `reference-analysis`、`parity-contract` |
| 执行状态、产品输入、迁移方法 | `roadmap`、`product-strategy`、`migration-guide` |
| 验证方法与报告 | `verification`、`verification-plan`、`verification-record`、`manual-verification`、`implementation-verification`、`architecture-review` |
| 失效表达与历史入口 | `archive` |

规范接受与实现状态分别表达，`accepted` 不等于 `implemented/complete`。
参考分析给出仓库、提交和稳定 class/method；规范给出范围、失败、扩展点和验证入口。

## 链接与门禁

文件使用小写 kebab-case，固定入口为 `00-index.md`。
移动或删除后检查 doc、book、启动文件及其他仓库引用；更新正文路径和锚点，
不只检查链接目标是否存在。每篇当前文档都应能从所属入口到达。

纯文档批次运行 `cargo xtask docs` 和 `git diff --check`。
文档门禁检查类型、本地路径、设计索引、parity 状态和规定入口中的命令；
design 全域另检查开头的能力归属、正文可达性与本地标题锚点。
冻结证据和 archive 的历史锚点豁免，路径仍须存在。

[设计检查规则](../tools/scripts/design_doc_rules.json)登记需要精确检查的有限关系：
当前四份协议的效力及示意 API、长文本局部接受范围、低 miter 替代条款、
FR-02 的基线角色与证据哈希。迁出编号在没有专题链接的段落中出现时，
工具只统计人工复核候选；历史批准与冻结证据不据此失败。
规则不是全文语义判断器，哈希也不能证明被审版本对应。

修改检查工具时运行
`python3 tools/scripts/test_check_design_docs.py`，用缺失归属、孤立页、坏锚点、
旧条款回流、基线误用与字节变化反例验证检查。
本批登记的 Rust 片段是协议示意，不要求编译；可执行消费者的编译入口见
[公开 API 与验证](../tests/README.md#公开-api-快照)。
新增可执行片段须关联实际存在的编译入口，不将示意代码冒充可运行示例。
design 之外的锚点与正文语义仍在本次修改范围内人工复核。
