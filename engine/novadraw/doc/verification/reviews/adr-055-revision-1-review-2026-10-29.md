## R1-01：多选拖动必须用一个锚点求批次平移

优先级：**P1**。位置：§3，183–203 行；关联 CE-DR06、CE-06/08/14。

§3 先要求各 source 独立映射，随后规定 D 将被拖动对象的
`S · G · grab_local` 平移到最新指针。该公式对单 source 完整，
但没有指定多 source 时由哪个对象求 D。不能让每个 source 都按自己的抓取点求 D。

逻辑反例：两个同父节点的抓取点在 surface 上分别为 x=10 和 x=110，
指针从第一个抓取点移动到 x=20。分别求 D 会得到 +10 与 −90，
两个抓取点最终都在 x=20，原有间距消失。共用 +10 则得到 x=20 与 x=120。
这些数值只用于说明公式，不是实现测试或性能数据。

**建议**：手势固定一个 anchor source 和其局部抓取点，由该锚点求唯一的
surface 平移 D。每个 source 仍使用自己的源父变换 Sᵢ，
候选几何为 `T⁻¹ · D · Sᵢ` 作用于各自约束几何。
共用 surface 平移不等于向不同父域加同一个模型增量。

建议补文：

> 多选拖动只保存一个手势锚点。由实际按下对象确定锚点；若该对象被祖先选择
> 覆盖而不在操作集合中，将按下位置转换到覆盖它的操作 source 的约束域。
> 锚点的选择规则固定且不依赖 hash 遍历顺序。每次更新使用当前锚点映射求出
> 一个 surface 平移 D，全部 source 共用 D，再分别进行父域映射。
> Ordered 策略仍可按插入位置布局，不承诺保留 XY 间距。

还需明确无直接按下对象的程序化手势如何选择锚点，以及约束局部映射 G
不可逆时如何表达抓取点。零宽/零高合法不应自动要求可逆的单位矩形缩放映射；
可以选择不把尺寸编码进 G 的约束局部域，或定义明确的合法缺失处理。

验证补充：CE-08 加入同父多选 XY 间距保持；CE-06 加入不同源父变换的多选，
逐项检查同一个 D；CE-14 验证静止指针下视口变化只求一次批次平移。
另覆盖按下被选祖先中的后代、零尺寸锚点、反向选择顺序和非 primary 对象启动拖动。

## R1-02：资格查询的 typed 连接需补齐

优先级：**P2**。位置：§2.1，110–117、130–156 行；关联 CE-DR02、CE-10/16。

受检 `PermissionQuery`、`PermissionDecision` 和 `PermissionReceipt`
已经说明了来源和绑定关系。剩余问题是 `ContainerMoveProtocol` 只关联目标计划
Request，没有说明 Tool 使用哪个 permission request，也没有给出其
Payload/Contribution 与查询、决定之间的类型关系。
“普通 typed permission request”尚不足以让第三方知道应在源父注册哪个 handler。

**建议**：选择并记录一种连接方式即可：

- 使用公开的统一 permission marker，其 Payload 为受检 PermissionQuery，
  Contribution 为 PermissionDecision；所有源父 policy 都通过同一个 builder 注册；
- 或由 ContainerMoveProtocol 关联 permission request 和 payload 构造函数，
  框架仍从受检 query 构造输入、校验决定并签发回执。

统一 marker 本身符合内置与扩展同模型，不要求为了开放性复制资格 request。
需要说明 metadata 是本次资格子批还是完整操作批次，并保证二者与受检 query
关系一致。再给出一次调用顺序：构造候选、查询资格、聚合目标计划、校验、反馈。
若选择先计算只读目标计划再查询源资格，也应明确该计划在资格齐全前不能受检或发布反馈。

无需在这一步补完所有 getter 或错误变体；本项只要求补齐类型与调用阶段，
使第三方能够写出相同注册和分派路径。

验证补充：CE-16 的外部 policy 注册真实资格 handler，由公共 Tool 完成查询，
验证 host、kind、精确子批及回执；不能直接构造回执来代替注册通道的证明。

## R1-03：不同关联协议在同一 Viewer 中如何协作需声明范围

优先级：**P2**。位置：§1、§2.1、§7，44–49、130–143、363–370 行；
关联 CE-DR02、CE-16。

两个不同的 `ContainerMoveTool<P>` 实例复用同一段状态机，能够证明关联类型开放，
但不能自动证明同一个手势能从 XY 容器进入只注册另一 request family 的 Ordered 容器。
Tool 的 P 在类型上固定，`P::Request` 不会随候选 host 改变。

例如当前 Tool 使用 XY 协议，目标 Ordered policy 只注册自身的另一 Request。
对该 host 的 XY 聚合得到无贡献，会继续探测祖先。这是现有 typed 分派的正常结果，
却可能让用户以为该 Ordered 容器已经支持当前拖动协议。

**建议**：明确首批协议适用范围，避免把“不同类型的两个消费者”
与“异构布局间的一个拖动手势”写成相同验收：

> 一个容器 Tool 实例固定使用其协议。参与该手势的源父和目标必须注册与该
> 协议匹配的资格及计划 handler。不同布局可以注册同一开放协议，
> 在各自 policy 内转换约束与决定插入位置。

如果首批只验证两个独立 Viewer/消费者，应明确这一限制。
如果首批要求 XY→Ordered 的同 Viewer transfer，则增加一个双方注册同一 active
协议的消费者场景；确有多协议组合需求再设计通用 typed 组合入口。
无需为此增加按内置布局类型判断的分派分支。

验证补充：CE-16 分别记录两个不同关联类型消费者，以及一个同 Viewer 的
XY→Ordered 场景；或把后者明确列为后续范围。验证不兼容 family 返回未支持，
不能据此宣称第三方布局拒绝了所有容器编辑。
