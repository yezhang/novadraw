# ADR-059：分阶段文字引擎与宽度复用草案评审

类型：`architecture-review`

日期：2026-11-02。能力归属：Core（`novadraw`）Text 引擎、分析资产登记及 Flow 调用。
Runtime 提供预算与候选发布依赖；Editor、backend、platform 无新增能力。
`api_semantics`：`text.flow`、`text.interaction`。

结论：建议修订后再批准。宽度复用方向可以保留，批准前应先补齐阶段身份绑定、
留存上界的证明责任和 registry 准入状态规则，再明确成本与默认启用条件。
本报告记录本次评审建议，不代表建议已被接受、契约已修订或实现已通过验证。
ADR-059 保持 `proposed`；实施状态仍以 [P2 backlog](../../roadmap/p2-delta-backlog.md)为准。

## R01 · P1：补齐阶段调用的身份绑定与校验主体

位置：草案 L79–94、L113–136，“所有引擎使用同一个可选能力”及资产登记章节。
原文要求“分析和 reflow 结束都重验引擎身份／revision”，
阶段接口却只提供 analysis key 和 registry，context 只描述预算和诊断。

草案尚未说明登记时的引擎身份由谁提供，以及 Core 如何检查扩展返回的 lease
确实属于本次引擎、registry、key 和输入。回调后只检查引擎身份／revision，
也没有覆盖 analysis key 或 registry 身份变化。

建议定义一次调用的绑定，包含引擎身份、revision、registry 身份和 analysis key。
Core 在回调前捕获绑定，在登记、读取和回调返回后均检查；
`analyze` 返回 `None` 时也先完成检查，再决定是否完整回退。
具体 API 形状可在实现设计中确定，但 ADR 应明确检查主体与执行顺序。

复核条件：能仅凭正文说明绑定的来源、Core 的校验入口和失效后的错误；
外部消费者覆盖回调期间 identity、revision、key、registry 变化，
以及返回 `None` 同时发生身份变化的情况。

## R02 · P1：明确留存上界的证明责任

位置：草案 L164–169，“字节准入与 Parley 前置条件”。
原句：“`TextAnalysisPayload` 必须提供可验证的留存上界。”

Core 不解释第三方 payload，无法独立确认内部数组容量和共享引用是否全部申报。
“受检登记”与“证明任意第三方 payload 的实际存储上界”需要分开说明。
不可变引用也不能自动证明 payload 没有通过内部可变性增加留存存储。

建议区分两层责任：生产者负责申报完整、有效且在 lease 生命周期内不增长的
存储上界；registry 负责检查计费描述的结构、算术、共享 backing 身份和额度。
这是扩展实现必须遵守的合同，不应表述为 Core 已验证任意第三方对象的实际内存。
补充内部可变性导致存储增长的禁止条件或重新准入规则。

复核条件：明确生产者的证明义务、Core 可检查的范围和存储增长约束；
不把一次自报字节数或受检登记等同于对第三方内部存储的独立验证。

## R03 · P1：补齐 registry 准入、失败与释放规则

位置：草案 L113–128、L160–172。
原文规定“缓存淘汰只释放缓存引用”，仍被 lease 持有的资产继续计费。

该方向可以保留，但登记过程失败、共享 backing 部分登记和 registry 销毁后的
计费凭证生命周期尚不明确。若条目淘汰被直接视为释放容量，
旧 lease 仍钉住的资产可能使留存额度失去约束。

建议补充以下状态不变量：

- 完成受检计费和额度预留后，才产生可用 lease。
- 登记失败释放本次临时预留，不留下计费泄漏。
- 淘汰条目时，仍被 lease 钉住的字节不能当作已释放容量。
- 计费账本随最后一个相关 lease 存活，registry 销毁不提前终止责任域。
- 请求副本、索引、计费凭证和共享 backing 登记表的 metadata 纳入计费。

复核条件：覆盖登记中途失败、共享 backing 去重、最后一个 lease 释放、
registry 销毁后仍持有 lease，以及“条目已淘汰，但旧 lease 仍使新资产无法准入”。
这些建议不要求回滚已经发生的缓存淘汰或外部引擎副作用。

## R04 · P2：说明 reflow 成本的单位与失败行为

位置：草案 L171–178。
原句：“reflow 的复制、行结果、导出及旧发布资产另记录。”
同段还要求“可知的复制成本在操作前准入”。

“另记录”未说明是诊断统计，还是能拒绝操作的预算扣费。
无法提供操作前计费依据时，阶段路径应如何退出也不明确。

建议用成本表区分模板留存字节、clone／断行／导出的 work 和 allocation 单位、
实际存储统计，逐项说明管理主体、扣费时点和失败行为。
明确无法提供必要计费依据时，reflow 返回结构化错误，
还是在进入阶段路径前就声明不支持；不能在执行后才把未知成本记成零。
保留“不保证瞬时峰值或 RSS”的现有限制。

复核条件：每笔成本能定位到单位、责任域与拒绝入口；
阶段与完整回退继续使用同一会话预算，并保持失败粘滞性。

## R05 · P2：把缓存拒绝路径纳入性能门禁

位置：草案 L142–145，“正常调用和失败”。
原文允许分析后无法准入时，在剩余会话预算内完整计算一次。

在零额度、超大输入或旧 lease 钉住额度的情况下，
可能先完成分析，再通过完整入口重新分析。持续 resize 时，
这条路径可能反复承担额外 shaping 成本。

建议允许对已知无法准入的情况提前返回 `None`。
分析后才发现无法准入时，仍按草案完整回退，并保留已发生成本。
性能验收增加零额度、容量不足、持续淘汰和首次布局，
报告分析次数、失败率及延迟，不能只比较热命中收益。

复核条件：区分提前拒绝与分析后拒绝，提供对应调用次数和成本数据；
不通过预算重置、忽略已发生成本或掩盖协议错误改善统计结果。

## R06 · P2：分开适配完成、正确性验证与默认启用

位置：草案 L186–191、L212–215。
原文在计费与代表性负载通过后允许启用 Parley 缓存，
但 Flow 完整等价安排在 C，匹配性能对照安排在 D。
默认启用究竟发生在哪一片，存在歧义。

建议 B 只完成计费接口和适配，C 完成受控接入与正确性验证，
D 再形成默认启用及默认限额的决策依据。
同时定义 C 的“精确等价”比较口径：几何与来源字段如何比较，
资源／provider handle 比较依赖绑定还是对象身份，
并覆盖 Unicode、inline、镜像和受约束 NoWrap 反例。

复核条件：明确各片允许启用的范围与前置验证；
适配完成不自动等于默认启用，正确性通过也不自动关闭整体性能验收。

## 建议保留的边界与后续复核

保留只去掉宽度、其余请求字段参与分析身份的保守投影；
保留内置与扩展共用阶段入口和 typed registry；
保留协议错误不以完整回退掩盖，以及 Parley 尚未满足计费前置条件的结论。
本报告不建议把编辑增量、inline 度量分离、worker 或原生 glyph 裁剪并入首片。

后续先回应 R01–R03，再明确 R04–R06。修订复核应逐项说明草案如何回应、
哪些仍待实施验证，不将本次建议记录作为批准或执行授权。
交付前已按技术文档清晰度与好好说话复核事实、逻辑和中文表达；
建议、反例与已执行验证分别标明，未进行独立复核。
