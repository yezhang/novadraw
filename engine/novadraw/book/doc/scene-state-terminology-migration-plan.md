## 2. 问题

“场景事实”原本用来强调一条架构约束：绘制、命中、布局、连接、输入和重绘范围都要从
同一个 Runtime 状态读取，不能各自维护一份互相冲突的副本。

这个约束成立，但“事实”不是合适的通用中文名称：

- Figure 拓扑、边界矩形、样式和可见性都会变化；
- 有些值由场景事务直接提交，有些值由稳定化过程计算；
- `SceneQuery` 读取的是具体数据项，不是一个抽象“事实集合”；
- “场景事实保持”看不出保持的是已提交状态、稳定状态还是后端资源；
- “场景事实仍可证明”缺少明确的所有者和一致性边界。

正文应直接说明状态所处的阶段，或说明查询读取了什么数据。

## 3. 术语裁决

“场景事实”不再作为三本书中的通用术语。根据语境使用下列名称。

### 3.1 场景源状态

场景源状态指 Runtime 直接拥有、由已接受场景事务写入的状态。典型内容包括：

- Figure 身份和拓扑；
- 显式设置的边界矩形、可见性和样式；
- 组件状态和资源引用；
- 作为后续稳定化输入的版本信息。

同一个字段在不同机制中可能承担不同角色。例如，应用显式设置的 bounds 可以是场景
源状态，LayoutManager 计算出的 bounds 则是派生结果。分类应看写入者和重建条件，不能
只看字段名。

### 3.2 已提交场景状态

已提交场景状态指 Runtime 已经接受并原子写入的场景状态前缀。它强调事务结果和写入
权威。

适用语境：

- 后端失败不会回滚场景事务；
- 表现状态不能回写 Figure 状态；
- Event callback 读取 callback 开始时的 committed prefix；
- Host 和 RenderBackend 不能修改 Runtime 中已经提交的状态。

已提交不等于稳定。一次事务提交后，布局、连接、文本排版或容器范围仍可能等待收敛。

### 3.3 稳定场景状态

稳定场景状态指某个 stable epoch 中，必须完成的派生工作已经闭合，绘制、稳定查询和
通知可以读取的一致状态。

适用语境：

- `StableSceneQuery`；
- 帧录制和重绘范围计算；
- 动画 Behavior 读取 stable facts；
- 观察者读取稳定结果；
- “场景仍然一致，但表面暂时不可用”一类失败说明。

稳定场景状态包含已提交源状态及其当前稳定派生结果，不包含表现覆盖、后端资源或已经
呈现的像素。

### 3.4 场景数据项

场景数据项指查询过程读取的具体值，例如：

- Figure geometry；
- parent/children topology；
- named anchor region；
- relative transform；
- visibility；
- revision 或 generation。

连接依赖追踪应写成“记录本次计算读取过哪些场景数据项”。如果重点是依赖图，可以直接
写“查询依赖项”。

### 3.5 场景状态

不需要区分提交和稳定阶段时，可以使用“场景状态”作为泛称。句子仍应写明所有者：

```text
Runtime 管理的场景状态
当前 Viewer 对应的场景状态
某个 stable epoch 的场景状态
```

不要单独写“系统中的场景状态”，也不要用“场景状态”包含表现平面或后端资源。

## 4. 替换表

| 当前表达 | 建议表达 | 判断依据 |
|---|---|---|
| 共享同一份场景事实 | 以同一份已提交场景状态为准 | 强调唯一来源 |
| Runtime 更新场景事实 | Runtime 提交场景状态变化 | 强调事务写入 |
| 稳定的场景事实 | 稳定场景状态 | 派生结果已经闭合 |
| 场景事实保持 | 已提交场景状态保持不变 | 后端或表面故障 |
| 后端不能改写场景事实 | 后端不能改写已提交场景状态 | 权限边界 |
| 缓存脱离场景事实 | 缓存与当前场景状态失配 | 缓存一致性 |
| 查询读取场景事实 | 查询读取场景数据项 | 查询和依赖追踪 |
| 场景事实仍可证明 | Runtime 仍能证明场景状态一致 | 故障与暂停 |
| scene facts | 场景查询数据；场景数据项 | 读者正文 |

下列词不采用：

- 场景真值；
- 场景真相；
- 场景语义事实；
- 场景事实集合；
- 权威事实层。

这些表达没有增加可验证语义，还会引入新的抽象词。

## 5. 与其他状态的边界

执行修改时，应保持以下关系：

```text
场景源状态
-> Runtime 原子提交
-> 已提交场景状态
-> 派生工作收敛
-> 稳定场景状态
-> 可选表现快照
-> 渲染提交包
-> 后端资源与像素
```

各层含义：

| 层次 | 所有者 | 是否可以反向成为场景权威 |
|---|---|---|
| 场景源状态 | Runtime | 已经是场景写入来源 |
| 已提交场景状态 | Runtime | 是当前提交前缀 |
| 稳定场景状态 | Runtime | 是查询和录制的一致读视图 |
| 表现状态 | Runtime Presentation Plane | 否 |
| 后端状态 | RenderBackend | 否 |

“业务源状态”另属应用模型。使用 Editor 时，Viewer 根据业务模型构建或同步 Part/Figure
视图；不使用 Editor 时，应用可以直接把部分场景状态作为显示权威。书稿不能暗示所有
应用都必须存在业务模型。

## 7. 非目标

本方案不修改：

- Rust 类型、函数、模块和测试名称；
- `StableSceneQuery`、`EventSceneQuery` 等公开或内部标识符；
- ADR-036 中的英文 `scene facts`；
- 业务模型与场景状态的权威归属；
- Runtime 提交、稳定化或帧协议；
- 历史审计证据和归档文档。

如果代码注释需要改进，应另建代码任务并运行对应测试。书稿 Agent 不应顺手修改源码。

## 9. 禁止的修改方式

- 禁止把“场景事实”全部替换为“场景状态”；
- 禁止把“场景源状态”“已提交场景状态”和“稳定场景状态”合并成一个词；
- 禁止把查询读取的数据项写成新的权威状态；
- 禁止把表现状态或后端资源归入场景状态；
- 禁止把业务模型描述成所有应用都必须具备的场景权威；
- 禁止修改源码标识符来配合书稿用词；
- 禁止按本方案中的旧行号覆盖并行 Agent 修改。

每个命中先归入以下一种语境：

```text
场景源状态
已提交场景状态
稳定场景状态
场景查询数据项
代码或规范原词
无法判定
```

“无法判定”需要检查 owner、写入入口、stable epoch 和重建条件，不能猜测替换。

## 10. 验收

### 10.1 定向搜索

```bash
rg -n '场景事实|scene facts|scene fact' \
  book/user book/internals book/contributor book/WRITING_PROFILE.md
```

读者正文中的“场景事实”应清零。剩余英文命中只允许出现在：

- 源码标识符或代码注释引用；
- ADR/规范原词说明；
- 本术语迁移计划。

### 10.2 语义检查

- 每处“已提交场景状态”都对应一次成功提交后的状态；
- 每处“稳定场景状态”都能关联 stable epoch 或派生收敛；
- 每处“场景数据项”都来自明确 Query；
- “场景源状态”不与业务模型、表现状态或后端状态混用；
- 后端失败不回滚已提交场景状态；
- 动画只覆盖表现状态；
- 图、表、标题和正文使用同一术语。
