# 技术文档写清楚

让读者仅凭正文和明确列出的阅读前提，理解问题、行为、依据和取舍。先修复解释，再处理措辞；保持技术含义与证据效力。

## 与好好说话衔接

本技能负责篇章结构、段落推理、信息顺序与解释完整性。[好好说话](../haohao-shuohua/SKILL.md)负责中文措辞、搭配、指代和句子节奏。按以下顺序使用：

1. 用本技能确定阅读任务、组织内容或诊断问题。
2. 完成授权范围内的起草或改写。
3. 用好好说话检查成稿的中文表达。
4. 回到本技能，确认措辞修改没有删掉定义、条件、因果、对比或结论限制。

结构诊断可以独立执行，不依赖其他篇章设计技能。好好说话不可用时，继续检查事实、句法、指代与搭配，说明未使用该技能，不宣称完成其流程。

## 确定任务和改动范围

先从请求与材料判断任务，不为已明确的范围反复询问：

| 任务 | 执行动作 |
|---|---|
| 起草 | 从材料建立问题、目标、行为、取舍和验证之间的关系；缺失依据单列，不编造 |
| 审查 | 引用原句与位置，解释理解障碍，给改法或待补信息；不自动改源文档 |
| 改写 | 先诊断再修改；允许在已授权范围内重组文字，保留完整语义与引用 |
| 轻改 | 只处理用户允许的措辞；结构问题给出建议 |

通读请求范围内的全文及必要上下文，先确定读者需要完成什么任务。局部材料不足以支撑全篇判断时，限定结论范围。

修改技术事实、架构取舍、验收目标或批准状态不属于表达改写。遇到含义不确定的地方，定向查已有材料；仍不能确定时保留歧义并列出待确认点。继续完成其他明确内容。

## 先锁定技术含义

起草时区分材料事实、设计建议与说明性假设；改写时双向核对原文与成稿：

- 保留数字、单位、代码、API 路径、公式、术语身份与出处。
- 保留执行主体、操作顺序、因果方向、适用范围、前提、例外和失败后的状态。
- 保留“必须／允许／建议／可能”等约束强度，以及设计、实施和验收状态。
- 不从测试数量、扫描结果、已接受 ADR 或已有示例推断实现完成。
- 原文每项必要信息在成稿中有下落；成稿每项事实在材料中有依据。

语言流畅不能弥补保真失败。只读参考、冻结评审和原始证据保持原文；在新报告中提出编辑建议。按仓库规则处理可服务正文、历史快照和唯一真源的分工。

## 按读者需要组织全文

先用一句话概括文档要解决的问题，再为各节指定它要回答的问题。以下是阅读任务，不是每篇必须套用的章节模板：

| 文体 | 读者需要得到的解释 |
|---|---|
| 方案 | 问题与影响、目标和范围、拟议行为、失败与恢复、取舍及验证方法 |
| ADR | 决策所回应的条件、所选方案、实质替代方案及代价；详细机制链接到专题 |
| 当前规范 | 谁持有状态、谁能操作、正常与失败行为、扩展及验证入口 |
| 首轮评审 | 被审规则、具体条件或反例、问题后果、建议及复核标准 |
| 修订复核 | 原问题、修订如何解决、支持依据、通过范围及剩余验证 |
| 完成记录 | 基线、实际改动、验证结果、证据与限制 |

在本仓库的方案和评审开头明确 Core、Editor 或其他 owner；跨层内容区分归属与依赖。保持状态和证据在既定入口维护。

先解释问题，再列追踪编号。先引入概念，再使用它推导其他规则。流程按发生顺序展开，先建立正常路径，再说明对应的失败分支。

开头给当前状态摘要；需保留的历史计划明确标为历史。与读者当前问题无关的过程记录移到所属记录并链接。调整标题时检查既有锚点引用，不能只删编号。

## 逐段检查解释是否完整

每段围绕一个问题展开。首句建立主题，后续句提供必要条件、机制、例子、证据或后果；允许其他清楚的展开方式，不强制固定句数。

逐段检查：

- **主体和动作**：谁检查、返回、提交或注销？“生命周期收口”“资格准入”是否省掉了关键动作？
- **指代和概念**：“两侧”“当前版本”“活动 P”能否唯一对应？项目新术语是否已定义或有精确链接？
- **条件和结果**：“需要时”“适当处理”“正确范围”是否掩盖了应当写明的条件？
- **句间关系**：后句是在解释、举例、推导还是转向另一个问题？读者是否需要自行补出关系？
- **论据和判断**：引用的规则、数据或反例是否足以支持该判断？设计意图是否被写成已验证结果？
- **层次和时间**：正常结果、错误、panic、发布校验是否被挤成一串？历史计划是否被当成当前要求？

有多个主体、阶段或独立判断时，按关系拆句或分段；长句结构清楚时保留。不要只加逗号却留下推理跳跃。

缺失的主体、条件或理由能从材料唯一确定时，补回已有含义并标明依据；不能确定时列为待补信息。新增说明性例子必须明确标为假设，不作为业务需求、原文事实或已执行测试。

## 选择合适的表达形式

保留精确代码名和标准术语，使用中文写明动作。“不 Debug 任意 Any”应表达为“不对任意 `Any` 值执行 `Debug` 格式化”。项目自定义术语补释义，不能用比喻替换机制。

斜杠串先辨明关系：并列、先后、替代或条件分别写清。审计编号和类型列表不能代替一句完整解释。

用列表表达并列任务，用编号表达步骤，用表格比较同类字段。单元格同时包含多条规则、反例和推理时，表格只留摘要与定位，将论证放回正文。

标题应帮助查找主题或结论。编号、并列、对比、连接词和必要总结按功能保留；不以数量、固定句长、回译顺畅或某种句式出现次数判断质量。

发现重复时，区分同义反复与必要的范围限制。删除前确认没有丢失前提、反例或证据效力。流程与授权限制可以集中说明或链接，仍须保留其约束。

需要示范改法或检查误改时，阅读 [审计案例与回归检查](references/audit-examples.md)；需要追溯方法来源时，阅读 [依据与适用边界](references/sources.md)。

## 交付前复核

分别回读事实、逻辑与措辞。结构调整后重新检查术语首次出现的位置、前向引用和章节锚点。

按文体做复述检查：仅凭正文及声明的阅读前提，能否讲清问题、关键步骤、失败行为、判断依据和取舍？规范、方案中的主要行为应能复述；评审中的“通过”应能说清通过什么、依据什么、还缺什么。

有独立读者时请其复述并记录误解；没有时做自审，明确限制。不要求每次另起评审流程，不假装已经独立验证。

机械扫描仅定位字面候选。实际使用扫描器时区分无匹配、发现候选与工具错误；检查代码、URL、引用等豁免。不得把工具失败报告为干净，也不得把零命中报告为逻辑或可读性通过。

按项目要求运行文档检查。仅改技能时验证 frontmatter、目录名及引用文件；只有新增脚本时才增加脚本验证，不为文字改写运行无关代码测试。

## 输出要让修改可审阅

审查结果先给主要发现，再按影响说明原句、位置、理解障碍、改法或待补信息。区分语言问题、解释缺口与技术疑问，不把文句不清直接判定为实现缺陷。

改写结果交付实际成稿，简要说明关键结构调整、保真核对及未解决歧义。只报告实际执行的检查；不伪造评分、通过数量或独立评审。

内容已经清楚时保留原文，不为满足清单制造改动。两技能的检查结果合并成一份简短交付说明，避免重复附上流程报告。
