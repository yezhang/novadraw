# 《Novadraw 贡献者指南》内容结构

## 全书主张

贡献者必须先确认权威状态、执行阶段和失败边界，再修改实现。代码结构服务于架构
契约；现有实现不能反向定义理想设计。稳定核心原理统一由《深入理解 Novadraw》
解释，本书只把这些原理映射到当前仓库的代码、规范和门禁。

全书沿一次贡献的因果顺序组织：

```text
识别责任域
-> 核验规范与语义
-> 明确所有权和不变量
-> 定义失败与提交边界
-> 实现最小变更
-> 定向验证
-> 扩大门禁
-> 代码评审
```

## 与另外两本书的分工

用户指南回答：

- 如何通过公开 API 构建应用；
- 如何使用已经存在的扩展点；
- 应用如何测试、排错和发布。

深入理解书回答：

- 图形编辑框架为什么需要这些结构；
- 状态、身份、坐标、更新和编辑协议如何协作；
- 哪些不变量不依赖当前源码布局而长期成立。

贡献者指南回答：

- 当前内部协议由哪些模块实现；
- 如何新增或修改扩展点；
- 如何保护跨模块不变量；
- 如何证明一次框架修改可以合并。

## 读者完成标准

读完后，贡献者应能：

1. 把变化定位到正确 crate 和 owner；
2. 区分权威状态、派生状态、缓存和临时反馈；
3. 分析 prepare、validate、commit 与 publication；
4. 区分基础协议、横切 Capability、共享模型和具体组件；
5. 修改 Runtime 或 Editor 时保持身份和事务边界；
6. 为失败、取消、stale identity 和部分发布设计负向测试；
7. 使用验证清单选择最小 suite 和最终门禁；
8. 判断何时需要 ADR、规范更新或公开 API 审计。

## 维护约束

- `doc/` 是规范事实源，本书不复制完整决策记录；
- 核心原理引用《深入理解 Novadraw》，本书不再平行维护第二套原理叙述；
- 已接受设计不等于已实现能力；
- 架构分析从需求和参考语义出发，不先扫描当前 Rust 实现；
- 实现任务先明确目标契约，再读取相关代码；
- 章节按因果顺序解释，不按文件逐项复述；
- 每个内部机制都必须说明所有者、失败模式和验证入口。
