# Novadraw 核心原理书稿更新提示词

下面的提示词用于下一次维护 `book/`。使用时可直接把“任务提示词”整段交给智能体，
并在末尾补充本次变更范围。

## 任务提示词

```text
请更新本仓库 `book/` 下的《Novadraw 图形引擎核心原理》，使其准确反映当前已接受
设计、实际实现和验证状态。

一、启动与事实边界

1. 严格按仓库启动门禁读取：
   - `AGENTS.md`
   - `CLAUDE.md`
   - 项目记忆（任务涉及架构、Draw2D/GEF、第三方源码或历史决策时）
2. 先读取 `book/README.md`、`book/SUMMARY.md`、`book/OUTLINE.md` 和全部现有章节，
   理解书稿结构后再修改。
3. 权威来源按以下优先级处理：
   - 已接受的架构决策记录（ADR）；
   - `doc/design/` 中范围更窄的规范性设计（`normative-design`）；
   - `doc/parity/` 的语义映射；
   - `doc/reference/` 的外部源码事实；
   - `doc/roadmap/` 的路线图实施状态；
   - 当前 Rust 实现与验证；
   - `book/` 的教学性解释。
4. 外部框架只允许对标 `/Users/bytedance/Documents/code/GitHub/gef-classic` 中的
   `org.eclipse.draw2d` 与 `org.eclipse.gef`。严禁使用 `org.eclipse.zest` 的源码、
   行为或产品语义定义 Novadraw 的需求、架构和实现。
5. 默认不要读取 `doc/archive/`。只有显式历史追溯时才读，并且不能把归档设计写成
   当前契约。
6. 不要把路线图计划、提案或仅存在的类型写成“已经实现”。“已实现”必须有当前代码
   和验证证据；当前状态只从图形核心/编辑框架路线图读取。

二、更新目标

1. 以因果顺序解释系统，而不是按文件逐个复述：
   - 平台输入或应用修改；
   - 场景运行时事务；
   - 图形树、节点状态与布局；
   - 派生状态收敛；
   - 校验收敛；
   - 计算重绘区域；
   - 录制绘制命令；
   - 渲染提交包与后端；
   - 编辑框架的“工具 -> 请求 -> 策略 -> 命令 -> 模型 -> 查看器刷新”。
   第 1 章必须维护一张总体渲染管线图，把上述阶段及后续章节的核心数据结构串联起来，
   并覆盖后端 `RenderOutcome` 返回 `Runtime::complete_submission` 的完成反馈。
2. 保持以下核心主题完整：
   - 系统公理、模块职责、所有权和身份域；
   - 边界矩形、内边距、客户区、视觉边界与投影边界；
   - 父级局部坐标、子内容变换、视口、缩放与矩阵顺序；
   - 图形对象、节点状态、图形树、生命周期与叠放顺序；
   - 递归渲染主线、裁剪、绘图状态、命令画布与后端；
   - 布局快照、布局输出、当前具体布局器、两阶段更新、类型化工作列表与稳定版本；
   - 命中测试、悬停、指针捕获、焦点、手势会话与分发结果；
   - 图层、自由范围、视口、滚动、缩放与边缘自动滚动；
   - 连接、锚点、场景查询、路由器、分组批次以及准备/校验/提交；
   - 模型适配器、编辑部件、查看器、选择、工具、请求、策略与命令历史栈；
   - 错误模型、故障锁定边界、验证与扩展方法。
3. 新增核心能力时，补充：
   - 概念关系图或时序图；
   - 数据结构及所有权；
   - 算法步骤与关键不变量；
   - 失败模式；
   - 实际代码锚点；
   - 自动测试、无窗口回放或人工验收入口。

三、写作规则

1. 中文为主。每章应能独立阅读：关键概念在该章首次出现时使用“中文名称（英文原名
   或代码名）”，并用一句话说明“它是什么、负责什么、必要时说明不负责什么”。
2. 首次定义后优先使用中文名称，不要在普通叙述中连续堆叠英文。仅在以下情况保留
   英文：
   - Rust 类型、trait、函数、字段、枚举值和命令；
   - Draw2D/GEF 固有类型名；
   - 中文译名可能产生歧义，需要保留英文原名以便检索。
3. 图、表头、章节标题和流程说明也优先使用中文；代码标识符保持源码拼写。不要只把
   定义集中到附录而让正文首次出现处仍然无解释。
4. 使用同一术语表达同一概念。推荐固定译法：
   - Figure：图形对象或图形行为（按上下文选择）；
   - bounds：边界矩形；client area：客户区；insets：内边距；
   - validation：校验收敛；damage：重绘损伤区域或简称重绘区域；
   - Layer：图层；Viewport：视口；Router：路由器；Anchor：锚点；
   - capture：指针捕获；feedback：反馈图形；faulted：故障锁定状态。
5. 图使用 Mermaid；优先 `flowchart`、`sequenceDiagram`、`classDiagram`。
6. 图按实际发生顺序从上到下或从左到右，不能打乱因果链。
7. 代码片段应短小，只保留解释契约所需的字段或步骤。引用当前实现时注明
   “实际接口摘录”；概念化内容注明“概念伪代码”。
8. 代码链接使用从 `book/` 出发的相对路径，并尽量同时写明类型/函数名。行号可作为
   辅助，但不能作为唯一定位方式。
9. 不复制大量源码，不逐函数罗列接口，不重复保存路线图状态表。
10. 明确区分：
   - 外部参考事实；
   - Novadraw 设计契约；
   - 当前实现；
   - 已验证状态；
   - 尚未实现或待人工验收。
11. 不发明未存在的类型、字段、测试、验证套件或命令。
12. 不把 `render_iterative.rs` 或 I 键切换写成当前能力。当前渲染主线是受保护的
   `novadraw-scene/src/graph/render_recursive.rs`，树深度上限为 10,000。
13. 对编辑框架明确保持三个身份域：
    `ModelId -> EditPartId -> FigureId`。命令不保存仍绑定当前编辑器或运行时的句柄。
14. 对自由范围反馈层明确保持：
    可扩展临时滚动范围、不被所在图层的固定边界裁剪、仍受最终视口裁剪。
15. 对边缘自动滚动明确保持：
    角区双轴滚动、固定逻辑表面指针位置、视口变化后同帧重投影、指针离开或取消时
    清理。
16. 对连接明确保持：
    带依赖追踪的场景查询、纯计算路由器、分组快照、准备/校验/原子提交，自环使用
    真实路径与折点几何。

四、执行步骤

1. 读取：
   - `doc/00-index.md`
   - 当前 ADR、相关 `doc/design/` 专题
   - Draw2D/GEF 语义对等账本
   - 图形核心与编辑框架路线图
   - `verification/suites.toml`
2. 用 `rg` 定位受影响类型、trait、算法函数和测试。只读任务相关代码，不做无关扫描。
3. 建立“书稿陈述 -> 规范 -> 实现 -> 验证”对照，先找出过期或缺失项。
4. 先更新主题章节，再更新：
   - `book/README.md`
   - `book/SUMMARY.md`
   - `book/OUTLINE.md`
   - `book/appendix-glossary-and-map.md`
5. 若书稿结构发生变化，同步修订本提示词。
6. 只修改 `book/`，除非用户明确要求同步其他文档或代码。

五、验证

1. 检查所有 `book/*.md` 相对链接指向存在文件。
2. 检查 `SUMMARY.md` 是否覆盖全部正式章节。
3. 检查每章新增概念的首次出现处是否有定义，并搜索普通叙述中可直接改成中文的英文
   词组；代码标识符不纳入此项。
4. 若布局实现或 demo 发生变化，核对 `impl LayoutManager for` 的产品实现、第 4 章
   布局器清单与 demo 样例是否一致；测试专用布局器不计入产品清单。
5. 若输入、Editor、派生状态、帧准备或后端提交协议发生变化，同步检查第 1 章总体
   渲染管线及其“管线阶段与后续章节”映射表。
6. 搜索并消除过期表述，例如旧路线图路径、已归档设计、迭代渲染主线、已完成能力
   仍写成目标等。
7. 运行：
   - `cargo xtask docs`
8. 若只修改 Markdown，通常无需运行全部 Rust 测试；如果 `cargo xtask docs` 的实现
   不覆盖 `book/` 链接，应额外执行本地链接检查，并在结果中说明。
9. 最后查看 `git diff -- book`，确认没有覆盖用户在 `book/` 中的并行修改，也没有
   修改其他目录。

六、输出

完成后简要报告：

- 更新了哪些章节与核心结论；
- 哪些陈述来自设计、哪些已有代码/测试证据；
- 执行了哪些验证及结果；
- 仍待人工验收或尚未实现的边界。

本次补充范围：
[在这里填写，例如“更新 G6 collaboration/persistence，补充新 Tool 与验证入口”]
```

## 使用说明

- 若本次只是修正一个链接或术语，可缩小读取范围，但仍要检查相关章节与
  `SUMMARY.md`。
- 若变更涉及架构裁决，先更新架构决策记录、专题设计与语义对等账本，再更新本书；
  不要让本书先于唯一事实来源定义新架构。
- 若变更涉及核心代码但设计未变化，应核对代码锚点和验证入口，不要把实现细节提升为
  新公理。
