# 《深入理解 Novadraw》维护规则

本页约束核心原理书的后续写作。

## 目标

本书解释长期稳定的框架模型、不变量和算法，不承担 API 手册或仓库操作指南的职责。
读者应在不依赖当前源码目录和路线图编号的情况下理解正文。

## 公共写作原则

更新正文前必须读取 [`book/WRITING_PROFILE.md`](../../WRITING_PROFILE.md)。本书在公共
原则之上增加以下约束：

- 每章必须从真实矛盾和核心结论开始；
- 状态、身份、坐标和版本都要说明所属域；
- 过程按真实因果顺序描述，不按文件或类型顺序拼接；
- 拒绝、取消、可重试失败和故障锁定必须分开；
- 图必须表达因果、所有权、身份映射、状态迁移或坐标关系；
- 不把当前实现目录、路线图状态或维护过程写成长期原理。

## 事实来源

更新前必须读取 `AGENTS.md`、`CLAUDE.md` 及任务相关项目记忆。事实优先级为：

1. 已接受 ADR；
2. 范围更窄的规范性设计；
3. Draw2D/GEF 语义账本与允许范围内的参考源码；
4. 当前实现和验证；
5. 本书解释。

不得使用 `org.eclipse.zest` 定义 Novadraw 需求或架构。默认不读取 `doc/archive/`。

## 写作规则

- 从问题和第一性原理开始，不从文件目录或 API 清单开始；
- 按实际发生顺序描述输入、变更、收敛、绘制和完成反馈；
- 每项状态都说明所有者、生命周期和重建条件；
- 每个算法都说明输入、输出、不变量、失败和复杂度；
- 区分当前稳定机制与尚未落地的设计，不把计划写成事实；
- 使用短小类型定义或伪代码解释协议，不复制大段实现；
- 不出现源码行号、roadmap 状态、提交步骤或临时审计结论；
- 不把应用配方写入本书，必要时链接用户指南；
- 不把文件修改和验证命令写入本书，必要时链接贡献者指南。
- 模型到视图使用“视图派生”“构建视图”“同步视图”或“重建视图”；几何跨域使用
  “坐标变换”“几何变换”或“表面包围盒”；普通叙述不使用未定义的“投影”。
- Runtime 直接状态使用“场景源状态”，提交后的前缀使用“已提交场景状态”，stable
  epoch 的一致读边界使用“稳定场景状态”，Query 读取的具体值使用“场景数据项”或
  “查询依赖项”；普通叙述不使用未限定的“场景事实”。
- 运行时帧协议依次使用“帧提交准备”“渲染提交包已就绪”“Host 提交后端”“帧已呈现”
  和“完成已确认”；普通叙述不使用“帧出版”，也不把提交包就绪写成已提交或已呈现。
  书稿和读者内容的出版边界继续使用“出版”。
- `Presentation Plane` 首次定义为“表现状态层”，`PresentationSnapshot` 称为“表现
  覆盖快照”，`FigurePresentation` 称为“图形准备结果”，`TemporaryVisual` 称为
  “动画临时绘制项”；普通叙述不使用“表现平面”。
- “表现”只描述 Runtime 中可丢弃的当前视觉状态，“呈现”只描述 surface 与后端的
  present 结果。动画临时绘制项不得与 Viewer 的 Overlay、Handle 或 Feedback 混用。

## 章节模板

1. 真实问题；
2. 核心结论；
3. 最小概念模型；
4. 数据、身份和所有权；
5. 按时间顺序的算法；
6. 不变量；
7. 失败与恢复；
8. 常见错误设计；
9. 与前后章节的关系；
10. 思考题。

## 更新触发

只有以下变化通常需要更新本书：

- 权威状态或所有权模型变化；
- 生命周期、因果顺序或原子提交边界变化；
- 坐标、布局、输入、连接或编辑协议的核心语义变化；
- 扩展模型或失败模型变化；
- 新证据推翻了书中的机制解释。

文件移动、API 改名、suite 调整或 roadmap 状态变化通常只更新用户指南或贡献者指南。
