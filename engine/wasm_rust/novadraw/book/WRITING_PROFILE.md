# Novadraw 书籍公共写作原则

**版本：** 0.1

**状态：** 试行

**适用范围：** Novadraw 用户指南、核心原理书和贡献者指南

## 1. 目标

本文件把《受控技术中文规范》中的通用规则提炼为适合技术书籍的公共写作原则。

它解决以下问题：

- 三本书对同一概念使用不同名称；
- 章节按模块罗列，缺少因果主线；
- 事实、设计、计划和示例混在一起；
- 状态、身份和副作用缺少明确所有者；
- 代码片段能够编译，但没有说明适用条件和失败行为；
- 句子形式正确，但读者仍无法建立完整心智模型。

本文件不替代：

- `AGENTS.md` 和 `CLAUDE.md`；
- 已接受的架构决策和规范性设计；
- 三本书各自的 `UPDATE_PROMPT.md`；
- 《受控技术中文规范》的完整规则。

## 2. 适用优先级

发生冲突时，按以下顺序处理：

1. 项目规范事实和当前实现证据；
2. 当前书籍的定位、内容边界和专用维护规则；
3. 本公共写作原则；
4. 章节局部表达习惯。

本文件控制表达方式，不定义第二份架构事实。

## 3. 三本书的共同目标

所有章节都应帮助读者完成以下至少一项目标：

- 理解一个稳定概念；
- 建立概念之间的因果关系；
- 正确使用一个公开能力；
- 安全修改一个内部协议；
- 判断失败发生在哪个边界；
- 找到可验证的完成条件。

如果一段内容不能直接服务上述目标，且只描述信息来源、项目历史、书稿维护过程或作者
推理过程，则不应进入读者正文。

## 4. 十二条公共原则

### BP-01 读者任务优先

每章开头应说明读者要解决的问题。标题和导言不应只写模块名称或类型名称。

**不推荐：**

> Runtime API

**推荐：**

> 应用如何把一次场景修改提交为稳定帧

### BP-02 结论先于展开

每节应先给出核心结论，再解释模型、原因、算法和例外。不得让读者阅读完整节后才能猜出
作者立场。

### BP-03 一个概念一个首选名称

同一适用范围内，一个概念只使用一个首选中文名称。英文原名和代码标识符用于首次定义、
检索或精确定位，不作为平行叙述名称反复切换。

术语改变时，应同步检查：

- 三本书的正文；
- 图、表和代码注释；
- 术语表；
- 章节间链接；
- 自动检查词典。

“投影”不能作为跨领域通用词。普通叙述必须按机制选择首选名称：

- 模型经过 Viewer、Part 和 Runtime 形成可重建视图，称为“视图派生”；动作明确时，
  直接写“构建视图”“同步视图”或“重建视图”；
- 点、矩形或视觉范围跨坐标域，称为“坐标变换”或“几何变换”，并写明源域和目标域；
- `projection`、`projected` 或 `project_to_*` 属于源码标识符时保留原名，首次出现时
  说明其中文语义。

只有真实的 projective transform、透视变换、降维、外部原文和旧术语讨论可以继续使用
“投影”。

“场景事实”也不能作为跨阶段通用词。普通叙述必须按状态阶段或查询对象选择名称：

- Runtime 直接拥有、由场景事务写入的状态称为“场景源状态”；
- Runtime 已经接受并原子写入的状态前缀称为“已提交场景状态”；
- stable epoch 中必需派生工作已经闭合的一致读边界称为“稳定场景状态”；
- SceneQuery 实际读取的 geometry、topology、transform、visibility 或 revision 等具体值
  称为“场景数据项”或“查询依赖项”。

不需要区分提交和稳定阶段时，可以使用“场景状态”，但必须写明由 Runtime 管理。源码
注释、ADR 或外部原文中的 `scene facts` 可以保留；读者正文必须按语境翻译。

“帧出版”不能用于运行时帧协议。普通叙述必须按实际阶段选择名称：

- Runtime 从稳定场景状态生成正式 `RenderSubmission` 的过程称为“帧提交准备”；
- `FramePreparation::Ready(RenderSubmission)` 称为“渲染提交包已就绪”；
- Host 调用 `RenderBackend::submit` 称为“提交后端”；
- `RenderResult` 为 `Ok(RenderDisposition::Presented)` 时，才称为“帧已呈现”；
- Runtime 接收完整结果并返回 `SubmissionAcknowledgement` 后，称为“完成已确认”。

书籍出版、成书边界和读者内容筛选仍使用“出版”。通用事务、通知和结构对外可见使用
“发布”。

“表现平面”不再作为读者正文的首选名称。首次定义使用“表现状态层
（Presentation Plane）”，后续按对象选择名称：

- Runtime 当前持有的动画覆盖值和树外动画临时绘制状态称为“表现状态”；
- 某个动画表现通道当前采样出的覆盖值称为“表现覆盖值”；
- `PresentationSnapshot` 称为“表现覆盖快照”，它是当前帧可选的稀疏只读输入；
- `FigurePresentation` 称为“图形准备结果”，它也用于普通 Figure 准备，不等同于
  动画表现状态；
- `TemporaryVisual` 称为“动画临时绘制项”，不与 Viewer 的 Overlay、Handle 或
  Feedback 混用。

“表现”用于 Runtime 中可丢弃的当前视觉状态；“呈现”用于 surface 和后端的 present
结果。无活动表现覆盖时，当前帧不生成表现覆盖快照，帧录制直接读取稳定场景状态。

### BP-04 首次出现即定义

概念首次出现时，应说明：

1. 中文名称；
2. 英文原名或代码名；
3. 它是什么；
4. 它负责什么；
5. 容易混淆时，说明它不负责什么。

定义完成后，普通叙述优先使用中文名称。

### BP-05 一个段落一个中心结论

一个段落只展开一个中心结论。概念书写不机械执行“一句一个动作”，但不应在同一段中
同时切换所有权、算法、性能和历史背景。

段落需要表达多个层次时，应拆成：

- 结论；
- 原因；
- 结果或约束。

### BP-06 按因果顺序叙述

涉及过程、协议或状态变化时，应按真实发生顺序书写：

```text
输入
-> 前置条件与身份解析
-> 候选计算
-> 校验
-> 原子提交
-> 派生状态收敛
-> 发布或呈现
-> 完成反馈
```

不得为了按文件或类型分类而打乱时间顺序。

### BP-07 所有权必须显式

介绍状态、身份、缓存、资源或副作用时，应说明：

- 谁创建；
- 谁长期拥有；
- 谁可以修改；
- 生命周期何时开始和结束；
- 失效后如何清理或重建。

“系统保存”“框架处理”“内部更新”不是充分的所有权说明。

### BP-08 坐标、身份和版本必须带域

提及点、矩形、ID、revision、epoch、session 或 frame 时，应说明其命名空间或语义域。

不得把以下对象写成可直接互换：

- `ModelId`、`EditPartId` 和 `FigureId`；
- 节点本地域、父内容域和逻辑表面域；
- 模型 revision、稳定 epoch 和渲染 frame；
- 已提交状态、表现状态和后端资源状态。

### BP-09 事实层次必须分开

正文应区分：

- 已接受且长期稳定的契约；
- 当前实现事实；
- 可替换的示例实现；
- 尚未落地的设计或提案；
- 教学伪代码。

计划、类型名称或路线图条目不能单独证明能力已经实现。

### BP-10 条件先于动作，失败紧随结果

程序、算法和修改步骤应先说明前置条件，再说明动作。动作之后应说明完成结果和失败路径。

推荐结构：

```text
前置条件
-> 操作或算法步骤
-> 预期结果
-> 失败与恢复
-> 验证证据
```

### BP-11 明确先于简短

可以拆分长句，但不得为了简短而省略：

- 动作对象；
- 坐标域；
- 身份域；
- 输入版本；
- 提交者；
- 失败状态；
- 验证条件。

句长只作为人工复核信号，不作为独立质量结论。

### BP-12 自动检查辅助，人工语义裁决

工具可以检查术语漂移、禁用词、失效链接、句长、标点和代码标识符。

工具不得独立决定：

- 架构解释是否正确；
- 因果关系是否成立；
- 示例是否代表稳定契约；
- 风险是否可接受；
- 书稿是否可以发布。

## 5. 公共术语规则

### 5.1 术语表示

首次出现时使用：

```text
中文名称（英文原名或代码标识符）
```

示例：

```text
重绘区域（damage）
场景运行时（Runtime）
渲染提交包（RenderSubmission）
```

代码、函数、字段、枚举值和命令保持源码拼写。

### 5.2 推荐译法

| 英文或代码概念 | 首选中文名称 | 说明 |
|---|---|---|
| Figure | 图形对象、图形行为 | 根据对象身份或行为协议选择 |
| Runtime | 场景运行时 | 代码引用保留 `Runtime` |
| bounds | 边界矩形 | 不笼统写“位置” |
| client area | 客户区 | 与边界矩形区分 |
| insets | 内边距 | 说明影响客户区时使用 |
| validation | 校验收敛 | 不仅表示参数检查 |
| damage | 重绘区域 | 必要时写“重绘损伤区域” |
| Layer | 图层 | 代码类型保留原名 |
| Viewport | 视口 | 与窗口或表面区分 |
| Router | 路由器 | 指连接路径策略 |
| Anchor | 锚点 | 指连接端点语义 |
| capture | 指针捕获 | 不简称“捕获” |
| feedback | 反馈图形 | 与后端完成反馈区分 |
| faulted | 故障锁定状态 | 表示不能继续普通操作 |
| Presentation Plane | 表现状态层 | Runtime 持有的可丢弃状态边界，不是坐标面或 Figure 图层 |
| presentation state | 表现状态 | 当前活动覆盖值和动画临时绘制状态的统称 |
| presentation override | 表现覆盖值 | 某个动画表现通道当前采样出的覆盖值 |
| PresentationSnapshot | 表现覆盖快照 | 当前帧可选的稀疏、只读覆盖集合 |
| presentation channel | 动画表现通道 | 类型化的动画目标槽位；定义后可简称“表现通道” |
| FigurePresentation | 图形准备结果 | 受检测量、视觉边界和不可变绘制数据，不专属于动画 |
| PresentationBinding<V> | 表现准备绑定 | 把类型化当前值准备成图形准备结果的能力描述 |
| TemporaryVisual | 动画临时绘制项 | Runtime 管理、树外、默认不可交互的绘制项 |
| RenderSubmission | 渲染提交包 | 后端消费的拥有数据 |
| model-to-view derivation | 视图派生 | Viewer 根据单一模型 revision 构建或同步 Part/Figure 视图 |
| view synchronization | 视图同步 | 已有 Viewer 消费模型变化并更新稳定视图 |
| coordinate transform | 坐标变换 | 点或向量跨明确坐标域 |
| surface bounds | 表面包围盒 | 几何变换到逻辑表面域后的保守 AABB |
| scene source state | 场景源状态 | Runtime 直接拥有、由场景事务写入的状态 |
| committed scene state | 已提交场景状态 | Runtime 已经接受并原子写入的场景状态前缀 |
| stable scene state | 稳定场景状态 | stable epoch 中必需派生工作已经闭合的一致读边界 |
| scene data item | 场景数据项 | SceneQuery 读取并用于依赖追踪的具体值 |
| frame submission preparation | 帧提交准备 | Runtime 从稳定场景状态生成正式渲染提交包的过程 |
| FramePreparation::Ready | 渲染提交包已就绪 | Runtime 已建立 in-flight，Host 尚未调用后端 |
| RenderBackend::submit | 提交后端 | Host 把渲染提交包交给后端 |
| RenderDisposition::Presented | 帧已呈现 | 后端确认目标表面已经呈现该帧 |
| SubmissionAcknowledgement | 完成确认结果 | Runtime 根据完整后端结果确认资源与恢复状态 |

### 5.3 禁止无定义切换

同一章节不应无定义切换以下表达：

- 节点、Figure、图形对象；
- dirty、damage、重绘区域；
- validate、validation、校验、稳定化；
- model、scene、presentation、backend state；
- 失败、拒绝、取消、故障锁定；
- 视图派生、坐标变换和未定义的 projection。
- 场景源状态、已提交场景状态、稳定场景状态和未加限定的“场景事实”。
- 帧提交准备、提交包已就绪、提交后端、帧已呈现和完成已确认。
- 表现状态层、表现状态、表现覆盖值、表现覆盖快照和图形准备结果。

如果这些概念确实不同，应分别定义。

### 5.4 高风险模糊表达

普通叙述中出现以下词语时，应检查是否可以替换为明确对象或条件：

- 相关、对应、适当、必要时；
- 通常、基本、可能、一般；
- 内部、系统、框架、自动；
- 处理、支持、完成、同步；
- 等、之类、某些、多种。
- 未说明所有者和树归属的“临时视觉”；
- 容易与后端 present 混淆的“呈现状态”“呈现快照”。

这些词语不是全局禁用词。只有在读者无法确定对象、条件、责任方或结果时才构成问题。

### 5.5 帧协议必须分阶段书写

描述帧生命周期时，必须保留以下因果顺序：

```text
场景状态稳定
-> 可选表现覆盖快照形成
-> 绘制命令录制完成
-> 渲染提交包已就绪
-> Host 提交后端
-> 后端返回 RenderResult
-> Runtime 确认完成结果
```

不得把“提交包已就绪”写成“帧已提交”或“帧已呈现”，也不得省略 Host 调用后端的
阶段。读者正文不使用“帧出版”“出版帧”“出版提交”或“出版权威”。ADR 标题、源码
标识符和引用原文保持原样。

### 5.6 表现与呈现必须分工

描述动画时使用“表现状态”“表现覆盖值”“表现覆盖快照”和“采样表现几何”。描述
surface 或后端结果时使用“可呈现”“帧已呈现”和“已经呈现的像素”。

`PresentationSnapshot`、`FigurePresentation` 和 `TemporaryVisual` 保留源码拼写，但
正文必须分别说明它们是表现覆盖快照、图形准备结果和动画临时绘制项。Viewer 管理的
Overlay、Handle 和 Feedback 仍使用 Figure 树协议，不属于表现状态层。

## 6. 事实与出版边界

### 6.1 后台核验与读者正文分离

ADR、路线图、语义账本、审计报告和第三方源码用于作者核验事实。是否进入正文由当前书籍
定位决定。

用户指南和核心原理书通常不展示：

- 结论来自哪个外部项目；
- 项目为何在多个方案中选择当前方案；
- 路线图推进过程；
- 审计批次和历史修复；
- 书稿如何维护。

贡献者指南可以提供规范和代码入口，但不应复制完整规范正文。

### 6.2 不把推断写成事实

仅存在以下证据时，不得声称能力已经实现：

- 一个类型名；
- 一段提案；
- 一个路线图目标；
- 一个未调用的方法；
- 一个仅测试专用的实现。

实现声明应同时具有行为入口和验证证据。

### 6.3 不引入第二份规范

书籍解释稳定事实，但不在正文重新定义 API、生命周期或错误合同。解释与规范冲突时，
先修正规范或实现，再更新书籍。

## 7. 图与表的公共原则

### 7.1 图必须表达关系

图应至少表达一种正文难以快速扫描的关系：

- 因果顺序；
- 所有权；
- 身份映射；
- 坐标转换；
- 状态迁移；
- 调用或提交链路。

只有若干方框和名词、没有关系含义的图不应保留。

### 7.2 图按真实顺序排列

时间和因果流程从左到右或从上到下。不得为排版美观打乱实际顺序。

### 7.3 图文使用相同术语

图中的节点、边和阶段名称应与正文一致。图不能引入未定义的平行术语。

### 7.4 表用于比较

两个以上对象需要按同一维度比较时，优先使用表格。表头应表达比较维度，不使用“说明”
作为万能列名。

## 8. 代码和示例

### 8.1 区分代码性质

代码块之前应注明以下一种性质：

- 实际接口摘录；
- 可运行示例；
- 概念伪代码；
- 简化数据结构；
- 命令输出。

### 8.2 示例必须闭环

面向操作的示例至少说明：

- 前置条件；
- 调用入口；
- 关键输入；
- 预期结果；
- 失败或错误返回；
- 验证方式。

### 8.3 不复制无关实现

代码片段只保留解释契约所需的字段和步骤。大段源码应改为链接类型、函数或模块。

### 8.4 不发明当前接口

教学便利不能成为发明公开类型、字段、测试或命令的理由。概念化内容必须明确标记为
伪代码。

## 9. 三本书的差异 Profile

### 9.1 用户指南

用户指南回答“如何使用公开能力完成应用任务”。

章节推荐结构：

1. 解决什么应用问题；
2. 从哪个公开入口进入；
3. 最小可运行用法；
4. 需要保持的不变量；
5. 常见失败和排查；
6. 如何验证结果；
7. 何时已经越过公共扩展边界。

用户指南应优先使用公开 API、可运行示例和应用结果，不展开内部演进过程。

### 9.2 核心原理书

核心原理书回答“为什么框架必须采用这些模型和因果约束”。

章节推荐结构：

1. 真实问题；
2. 核心结论；
3. 最小概念模型；
4. 数据、身份和所有权；
5. 按时间顺序的算法；
6. 不变量；
7. 失败与恢复；
8. 常见错误设计；
9. 与前后章节的关系；
10. 思考题。

核心原理书不依赖当前文件布局、路线图状态或临时实现细节。

### 9.3 贡献者指南

贡献者指南回答“如何安全修改当前仓库中的内部协议”。

章节推荐结构：

1. 要保护的架构边界；
2. 权威状态及其所有者；
3. 执行或提交的因果顺序；
4. 允许的扩展和禁止的捷径；
5. 失败模式；
6. 规范、代码和验证入口；
7. 评审问题。

贡献者指南可以链接当前源码和验证入口，但不能把当前目录结构提升为长期架构原理。

## 10. 章节写作合同

开始写一章前，应回答：

- 本章的目标读者是谁？
- 读者读完后能做出什么判断或完成什么任务？
- 本章的核心结论能否用一句话表达？
- 本章新增哪些术语？
- 哪些状态和身份需要明确所属域？
- 本章描述的是事实、设计、提案还是示例？
- 本章的因果起点和结束点是什么？
- 失败发生后，哪些事实保持不变？
- 哪些内容属于另外两本书？

章节完成后，应检查：

- 标题是否表达问题或任务；
- 开头是否给出结论；
- 每个概念是否在首次出现时定义；
- 是否存在术语漂移；
- 是否按真实因果顺序展开；
- 所有者、身份域和坐标域是否明确；
- 是否区分拒绝、取消、失败和故障锁定；
- 图表是否与正文一致；
- 示例是否标明性质并形成闭环；
- 是否引入未核验事实；
- 是否重复其他书的职责。

## 11. 自动检查建议

### 11.1 可作为错误

- 正式章节链接不存在；
- `SUMMARY.md` 引用不存在文件；
- 使用已明确禁用的旧术语；
- 同一代码标识符出现多个中文译名；
- 代码链接目标不存在；
- 读者可见页面含 `TODO`、`TBD` 或占位文本；
- 书稿声称运行的命令在验证清单中不存在。

### 11.2 可作为警告

- 句子超过建议长度；
- 一个段落包含多个主题；
- 出现高风险模糊词；
- 首次出现英文概念但没有中文定义；
- 图中术语与正文不一致；
- 大段代码没有说明性质；
- “系统”“框架”“内部”没有明确责任对象；
- “失败”没有说明状态是否已经改变。

### 11.3 必须人工评审

- 架构解释是否符合事实；
- 因果顺序是否正确；
- 所有权是否准确；
- 示例是否误导扩展边界；
- 失败与恢复是否完整；
- 是否把当前实现细节写成长期公理；
- 是否把计划写成已实现能力。

## 12. 维护规则

### 12.1 更新触发

以下变化应检查本文件：

- 三本书出现新的共同术语；
- 两本以上书籍重复同一写作约束；
- 自动检查新增公共规则；
- 公共章节合同发生变化；
- 《受控技术中文规范》改变术语或句法原则。

### 12.2 不在此处维护的内容

以下内容保留在各书的 `UPDATE_PROMPT.md`：

- 事实来源优先级；
- 允许读取的源码和外部参考范围；
- 当前实现状态；
- 专用章节模板；
- 特定 API、算法或验证门禁；
- 各书独有的出版边界。

### 12.3 验证

书稿交付前至少执行：

```bash
cargo xtask docs
git diff --check
./tools/scripts/build_book.sh
```

并人工确认：

- 三本书对同一概念使用同一首选名称；
- 各书没有越过自身内容边界；
- 书籍解释没有成为第二份规范事实；
- 自动检查结果已经过人工裁决。
